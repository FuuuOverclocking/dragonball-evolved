分支 lifecycle-control（3757132）· 状态 待你确认 · 尚未改动任何代码

1

先修所有权

快照不再持有 RAM。GuestRam 是唯一所有者，rebuild 按值接收它，所以两台 VM 共用一块 RAM 在类型上就不可能。

2

区域分种类，窗口进账本

启动 RAM、热插 RAM、设备窗口分开建模。设备内存窗口紧跟 RAM，grant 记入 plan，恢复时重放。

3

用 virtio-mem 检验抽象

按 chunk 动态绑定 KVM slot。"先解绑 → 再确认 → 最后 unmap"由句柄类型保证。快照持久化放在最后。

读法：每节第一行是结论，图在前，细节默认折叠。第 3 节的地址图、第 4 节的所有权图、第 5 节的时序图都可以交互；第 12 节可以直接点选并生成回复。

术语先对齐几个词

GPA / HVA
guest 物理地址 / 宿主虚拟地址。
memslot
KVM 中"一段 GPA → 一段 HVA"的映射条目，按编号管理。已有 slot 只能删除或移动，不能改大小。
plan
启动前一次算好的布局（纯数据）。快照记录它，恢复时照搬，不重新计算。
grant / replay
grant 是从值类型账本分到的一段地址或一个 GSI，记在 plan 里；replay 是恢复时在新账本上逐个 reserve 记录过的 grant。
DMA 视图
设备读写 guest 内存用的 GuestMemoryMmap 值（目前是 SharedGuestMemory），由 Activation 按值交给设备。
block / chunk
block 是 virtio-mem 插拔的最小单位（默认 2 MiB）；chunk 是本计划新引入的 KVM slot 粒度（默认 128 MiB），一个 chunk 内有任一块已插就保持绑定。
discard
释放宿主页但保留映射：匿名内存用 MADV_DONTNEED，memfd 用 MADV_REMOVE（等同打洞）。

够用、可以沿用的部分

  • 值类型账本：再加一个设备内存池即可。grant 记在设备 plan 里，恢复时 replay 重放，与 virtio-mmio grant 同一种做法。
  • KvmVm 拥有内存，KvmVcpu 持有 Arc<KvmVm>：映射比所有能访问它的 fd 活得久，这个结构可以推广到运行期绑定。
  • 设备经 Activation 按值拿到视图，并有自己的控制 channel：已经具备"按值下发新视图 + oneshot 确认"的形状。
  • vCPU 线程不直接读写 guest 内存：所有访问都经过 KVM，内存变化不需要通知 vCPU 或总线。

为什么设备窗口不进 DMA 视图（第一版）

只读 pmem 的映射如果在视图里，guest 只要让 virtio-blk 往那里写，整个 VMM 就会 SIGSEGV，违反"局部故障就地隔离"。代价是 guest 对 DAX 页做 O_DIRECT 会得到 I/O 错误。firecracker 和 cloud-hypervisor 同样不放；QEMU 则把它们全部纳入地址空间。

    e820（PVH memmap）

      virtio-mem 区和 pmem 窗口都不在 e820 中：guest 只经 virtio 配置空间得知它们。

      账本

      ResourceBook 增加 device_memory: AddressPool；resource_book() 改为接收 &MemoryPlan。窗口与 RAM 由同一个纯函数给出，二者不相交由构造保证。

      对齐

      • 窗口起点、virtio-mem 区：1 GiB
      • chunk 128 MiB，block 2 MiB
      • pmem / DAX 窗口：2 MiB

      纯校验（plan 阶段）

      • 全部 grant 末端 ≤ 2phys_bits
      • memslot 预算 = RAM 段数 + Σ chunk 数 + 窗口类设备数 ≤ 32764
      为什么紧跟 RAM，而且不超过 1 TiB
      • PVH 直接进入 vmlinux 时没有 KASLR_FLAG（只有 bzImage 解压器会设置它，boot/compressed/kaslr.c:855），guest 的可热插上限只是 MAX_PHYSMEM_BITS。
      • 如果以后支持 A2（bzImage），内存 KASLR 会把上限压到 (ceil(RAM / 1 TiB) + padding) TiB（mm/kaslr.c:109-110）。kangaroo 的 padding 是 1 TiB；超出的部分 guest 只告警并弃用（这个 6.6 内核回移了 physmem_end）。
      • 紧跟 RAM 且不超过 1 TiB，在两种启动方式下都安全。窗口记录在 plan 中，以后改了布局函数也不影响旧快照。

      谁持有映射

      "先解绑 → 再确认 → 最后 unmap"由什么保证

      ①

      先解绑

      Binding::unbind(self) 只在删除 slot 的 ioctl 成功后才返回映射；失败就把句柄原样还回去。

      KVM 在 ioctl 返回前已执行 synchronize_srcu_expedited（kvm_main.c:1673）。Drop 时删除失败：泄漏映射，绝不 unmap。

      →
      ②

      再确认无人访问

      VMM 内的访问者都通过视图值访问；新视图下发后，各自回 ack，就表示已放弃旧视图。

      外部访问者（以后）：vhost-user 对 REM_MEM_REG 的应答、VFIO unmap 的返回。

      →
      ③

      最后 unmap

      munmap 发生在最后一个 Arc 被 drop 时（vm-memory 的 MmapRegion）。

      任何还可能访问的一方都持有 Arc，所以不会过早 unmap。

      slot 号由 Machine 持有的值类型 IdPool<MemSlot> 分配，在 attach 时按 plan 给每个设备预留一段（单一所有者，不需要锁）；slot 号仍不进 plan，也不进快照。绑定由设备自己持有、不经 vmm-main，可避免"设备等 vmm-main 回复，而 vmm-main 在 Busy(pause) 中等这个设备 quiesce"的死锁。

      5virtio-mem：插拔时序

      结论：纯核 handle() 返回新状态和有序的副作用列表，外壳按顺序执行。插入时先 Bind 再 ACK；拔出时先 Unbind，再 discard，最后 ACK。

      对照：cloud-hypervisor 的顺序是反的

      拔出时先 discard、后做 DMA unmap；插入时先改 bitmap 再 map，中途失败也不回滚（virtio-devices/src/mem.rs:518-556）。本计划用纯核的副作用列表固定顺序，并在单测里断言。

      设备层面的几个要点
      • 要求 guest 协商 VIRTIO_MEM_F_UNPLUGGED_INACCESSIBLE：协商后 guest 不得访问未插的块，才能把空 chunk 从 KVM 解绑。kangaroo-6.6 的驱动支持它（virtio_mem.c:3443-3448）；firecracker 同样强制要求。
      • 块状态放在会话之外：规范要求设备复位不得改变块的插拔状态（mem/description.tex:174），所以 bitmap 属于设备任务本身，而不属于某一次激活。
      • 插拔状态只存一份：按块记在 MemState 里，chunk 是否绑定由它推出。firecracker 按 slot 和按块各存一份，恢复时也不核对两者。
      • 未插的 chunk 仍保持映射（只是 discard 过）：guest 违反协议的 DMA 只会重新分配宿主页（上限是区域大小），不会让 VMM 崩溃。
      • 放在 io 线程：ioctl 和 madvise 可能耗时毫秒级，不能阻塞 vmm-main（D5）。
      • transport 要改：配置空间改为由设备发布、transport 读取；实现 ConfigGeneration（0x0fc）和配置变更中断。

      7快照：先修所有权，区域模型先于持久化

      结论：本阶段第一步就让快照不再持有 RAM。持久化放在最后，因为内存镜像只是区域模型的一个投影。

      现在

      内存镜像 = 区域模型的投影

      启动 RAM全量；memfd 用 SEEK_DATA 跳过空洞
      virtio-mem 区只存已插的块（由设备快照里的 bitmap 决定）
      pmem / DAX不进镜像：文件即内容，或由设备重建

      如果先定镜像格式，就会把"所有区域都是稠密 RAM"固化进去，所以持久化排在区域模型和 virtio-mem 之后。

      持久化（M5）

      • MachineSnapshot 加版本头与 CRC（firecracker：bitcode + CRC64，只认同一主版本）
      • 一个稀疏镜像文件，manifest 显式记录每段的文件偏移（firecracker、cloud-hypervisor 都由区段顺序隐含偏移，镜像没有头和版本）
      • 恢复先做 Copy；MAP_PRIVATE 写时复制和 uffd 以后再加

      热升级（E10）

      memfd 后端时，GuestRam::into_fds(self) 交出所有权，借 API 已有的 fd 传递机制发出去；新进程用 GuestRam::adopt 接收，全程零拷贝。cloud-hypervisor 的本地迁移就是逐个 slot 发送 memfd。

      dirty tracking（最后）

      KVM 侧：只改已有 slot 的 flags（kvm_main.c:2108-2109 允许）。VMM 侧：视图的 bitmap 类型参数从 () 换成 Option<AtomicBitmap>。slot 号不持久化，所以脏页按 GPA 区间记录。
