vmm-main 主循环里的状态迁移

从 crates/vmm/src/lib.rs:41 的 start() 出发：它创建请求通道、启动 vmm-main 线程，在单线程 LocalRuntime 上运行 main_loop::run。主循环每轮等待一个输入，把它交给 controller 中的纯决策函数，再执行返回的 Next。本页逐层拆解这个过程：状态由什么构成、每轮循环做什么、每种输入在每个状态下导致什么、退出原因如何合并。

crates/vmm/src/lib.rs crates/vmm/src/main_loop.rs crates/vmm/src/main_loop/controller.rs crates/vmm/src/vmm_server.rs crates/vmm/src/machine/state.rs
状态是一个值Controller 枚举，加上循环里的两个局部变量 server 与 stopping。
决策与执行分离controller.rs 消耗旧状态、返回 Next；副作用都在 main_loop.rs。
一次只等一个输入biased select!：事件 ≻ 操作完成 ≻ 请求。
操作从不被取消Start / Pause / Resume / Resize / teardown 都等它们自己结束；失败的机器只能 teardown。
01

入口：从 start() 到 serve()

调用方只拿到一个可克隆的 VmmClient；真正的生命周期全部在 vmm-main 线程里，由一个 future 串行推进。

调用方线程
  1. start(ctx) 创建 mpsc::unbounded_channel
  2. 接收端包成 VmmServer::new(rx)，移入新线程
  3. 返回 VmmClient { tx, JoinHandle }

客户端用 send / call / call_timeout / call_async 发请求，每个 VmmRequest 自带一次性 reply。join_vmm_thread 取回线程返回的 VmmExitStatus。

VmmRequest →
所有 VmmClient 被 drop
⇒ 通道关闭 ⇒ Inbound::Detached（只报告一次）
← VmmExitStatus
vmm-main 线程
  1. vmm_main 构建 current-thread LocalRuntime（失败 → VmmExitStatus::Error）
  2. block_on(main_loop::run(server, &ctx))
  3. serve(server, ctx, NotStarted(MachineSpec::default()))
  4. 循环直到某条路径 return VmmExitStatus

设备 future 也跑在这个 runtime 上，可以是 !Send。Instance { id, version, update_logger } 是回答请求所需的进程信息——除 KVM 之外的一切。

02
状态由什么构成

  
"主循环的状态"并不只是 Controller。serve() 里还有两个可变局部变量，它们共同决定下一轮等什么、如何退出。

  

    

      
controller: Controller<Machine, PausedMachine, FailedMachine>

      
    
        
  • NotStarted (MachineSpec) 配置以不可变值累积
    • 
        
  • Running (Live<Machine>)
    • 
        
  • Paused (Live<PausedMachine>)
    • 
        
  • Busy 操作进行中，机器被保留到它自己结束
          
      
            
    • Starting(Starting<Machine>)
      • 
            
    • Pausing(Transition<PausedMachine, FailedMachine, PauseError>)
      • 
            
    • Resuming(Transition<Machine, FailedMachine, ResumeError>)
      • 
            
    • Resizing(Resizing<Machine>)
      • 
          
    
        
    • 
      

      
Live<M> = { machine, events }。注意没有 Failed 变体：F 只出现在失败结果里，"带着失败的机器继续服务"在类型上不可表示。

    

    

      
server: Option<VmmServer> — 准入

      
    
        
  • Some：可以接收请求。
    • 
        
  • None：准入关闭。drop 接收端会丢弃队列里尚未出队的请求及其 reply，客户端得到 CallError::NoReply；之后的 send 返回 ServerStopped。
    • 
        
  • next_inbound 在 None 时永久 pending，不会让 select! 空转。
    • 
        
  • 收到 Detached 后 VmmServer 内部的 rx 变为 None，同样永久 pending，但 server 仍是 Some。
    • 
      

      
vmm_server.rs:11-44 · main_loop.rs:365-370

    

    

      
stopping: Option<Exit> — 待执行的退出

      
    
        
  • None：正常服务。
    • 
        
  • Some(exit)：已决定退出，原因已记录；后续原因只通过 prefer_exit 合并进来，不会被清除。
    • 
        
  • 下一轮入口 take() 它：稳定状态立即 teardown 并 return；非 Resize 的 Busy 原样放回，继续等操作完成。
    • 
      

      
不变量：stopping.is_some() ⇒ server.is_none()。每个设置 stopping 的位置都同时关闭准入。

    

  

  

    
GetInstanceInfo 报告的 VmState：操作进行中报告它的出发状态

    

      
NotStartedStarting→ NotStarted

      
RunningPausingResizing→ Running

      
PausedResuming→ Paused

04
一轮循环的八个步骤

  
serve() 的 loop 体按固定顺序做八件事。只有第 ③ 步会 await 输入；第 ② 和第 ⑧ 步可能直接 return 结束线程。点开每一步查看对应源码。

  
    
    
  1. 
      ①入口：检查内存服务是否失效main_loop.rs:54-63, 242-251
      
    
        
    服务退出可能丢掉热插拔 RAM 仅有的注册，所以每轮等待前都检查真实 owner，不论上一轮是被什么唤醒的。只能检查机器在 operation 之外的状态：Running、Paused、Resizing。Starting / Pausing / Resuming 的机器在 future 里，不能为了检查而取消它，留给第 ④ 步。
    
        
    命中时：server = None，stopping = Some(MemoryServiceFailed(window))。已经在 stopping 时跳过——停止过程中服务退出是预期的。
    
        
    
      
    
    
    2. 
    
  2. 
      ②处理待执行的退出main_loop.rs:64-82
      
    
        
    stopping.take() 之后按状态分三种：
    
        
      
          
    • Resizing → return shutdown_resize(…)。发布可能要等 CPU / 内存服务 teardown 释放卡住的内存才能结束，必须两者并发。
      • 
          
    • Starting / Pausing / Resuming → 把 stopping 放回，继续本轮。CPU 迁移不可取消。
      • 
          
    • NotStarted / Running / Paused → return teardown(state, exit)。
      • 
        
    
        
    
      
    
    
    3. 
    
  3. 
      ③等待一个输入main_loop.rs:83, 318-381
      
    
        
    next_input(&mut controller, &mut server) 只借用状态里的 operation：输掉一轮 select! 不会 drop 它。分支按 biased 顺序轮询，事件永远优先——当 reset 和 PauseError::Exited 同时就绪时，先记住 reset，而不是把它当成致命错误。
    
        
    
          
    状态分支（优先级从左到右）产生的 Input
    
          
            
    NotStarted请求Inbound
    
            
    Running Paused事件 → 请求Event / Inbound
    
            
    Starting事件 → operation → 请求… / Started(Result<Machine, StartError>)
    
            
    Pausing事件 → operation → 请求… / Paused(Result<PausedMachine, (FailedMachine, PauseError)>)
    
            
    Resuming事件 → operation → 请求… / Resumed(Result<Machine, (FailedMachine, ResumeError)>)
    
            
    Resizing事件 → operation → 请求… / Resized(Result<(), MachineResizeError>)
    
              
        
    
        
    next_event 内部也是 biased：machine 事件（GuestReset / VcpuFailed）先于设备退出；两个源都关闭后永久 pending。next_inbound 在 server 为 None 时永久 pending。
    
        
    
      
    
    
    4. 
    
  4. 
      ④输入后再检查内存服务main_loop.rs:84-103
      
    
        
    一次完成可能把机器"交还"出来：Started(Ok) / Resumed(Ok) 交回 Machine，Paused(Ok) 交回 PausedMachine。在它被装进新状态之前就检查其内存服务；同时也再查一遍当前状态。必须在 reset 等事件把循环带入 stopping 之前做，否则服务的正常 Stop 会被误判为丢失 RAM 依赖。
    
        
    
      
    
    
    5. 
    
  5. 
      ⑤完成后补收 final-poll 事件main_loop.rs:104-125
      
    
        
    operation 可能在最后一次 poll 中往事件通道里塞了一个事件——此时事件分支已经被轮询过了。如果不补收，Start 失败时它会随 events 一起被丢掉，或者从完成直接走到 teardown 时被忽略。因此每次收到完成类输入，都用 try_recv 把 machine 事件抽干，合并进 stopping 并关闭准入。
    
        
    对应测试：events_queued_in_a_failed_starts_final_poll_are_not_lost（main_loop.rs:759）。
    
        
    
      
    
    
    6. 
    
  6. 
      ⑥已在退出时，Start 的 resume 失败也要记入原因main_loop.rs:126-135
      
    
        
    正常情况下 StartError::Resume 是可重试的：回到 NotStarted(spec)，原因只体现在回复里。但如果已经在 stopping（比如先收到了 reset），回到 NotStarted 后会直接退出，这时 resume 失败本身必须进入退出原因，否则一个良性的 reset 会掩盖致命的 CPU 或内存依赖故障。
    
        
    
      
    
    
    7. 
    
  7. 
      ⑦交给 controller 决策main_loop.rs:136-174 · controller.rs
      
    
        
    按 (状态, 输入) 匹配到 controller 的纯函数：on_inbound（请求 / Detached）、on_event、on_started、on_paused、on_resumed、on_resized。它们按值消耗旧状态，能立刻回答的就地回复，返回 Next。由于 next_input 只 poll 当前状态自己的 operation，其余 (状态, 完成) 组合都是 unreachable!。
    
        
    controller 泛型于 R / P / F，测试里用 Running(u32)、Paused(u32)、FakeFailed(u32) 驱动，无需 KVM。
    
        
    
      
    
    
    8. 
    
  8. 
      ⑧执行 Nextmain_loop.rs:175-238
      
    
        
    
          
    Next外壳做什么之后
    
          
            
    Stay(state)无继续循环
    
            
    Start(spec, reply)start()：在 vmm-main 上同步 plan + build（读 kernel / initrd，构建 parked 机器，guest 尚未运行），再由 on_built 决定状态Starting 或 NotStarted
    
            
    Pause(running, reply)Transition::new(running, reply, |m| m.pause())Pausing
    
            
    Resume(paused, reply)Transition::new(paused, reply, |m| m.resume())Resuming
    
            
    Resize(running, size, reply)同步 machine.resize_memory(size)；成功得到只等待发布的 futureResizing；同步失败回复 Err 留在 Running
    
            
    Exit(state, exit)server = None；stopping = prefer_exit(stopping, exit)状态不变，下一轮第 ② 步处理
    
            
    Terminate(Live<F>, exit)关闭准入，合并原因，return poll_teardown(failed.teardown(), events, exit)终止
    
            
    StartTeardown { error, events }关闭准入，原因置为 StartTeardown，补收事件，算出状态，最后才 drop 残留 owner终止

06
退出原因如何合并

  
进入 stopping 之后仍会有新的原因到来：迟到的 vCPU 故障、操作失败、teardown 期间的事件。prefer_exit(prior, next) 决定保留哪一个；exit_status(exit, teardown) 把最终原因映射为线程返回值。

  

    

      
优先级（高 → 低）

      
    
        
  1. StartTeardownStart 的清理失败：资源可能仍被持有
    2. 
        
  2. VcpuFailed来自 vCPU 线程的真实故障事件
    3. 
        
  3. MemoryServiceFailed · MemoryServiceResumeFailedRAM 依赖丢失，或无法证明 resume 安全
    4. 
        
  4. TransitionFailedCPU 超时、panic 或 join 失败
    5. 
        
  5. GuestReset ≻ TransitionExited已退出的 CPU 由 reset 事件解释，属正常
    6. 
        
  6. TransitionExited ≻ Shutdown · Detached没有事件解释的 CPU 退出是错误
    7. 
        
  7. Shutdown · Detached · GuestReset彼此之间先到者保留
    8. 
      

      
前四级中同级相遇时后到者胜出。第 5–7 级不是全序：结果可能依赖到达顺序（见第 07 节的边角）。

      
exit_status

      
    
        
  • teardown 返回 Err → 覆盖一切：Error("tear down the machine: …")。已回复 Ok 的 Shutdown 无法再报告它，只有线程状态能。
    • 
        
  • Shutdown / Detached / GuestReset → VmmExitStatus::Ok
    • 
        
  • 其余 → VmmExitStatus::Error(渲染后的错误链)
    •

    07
    设计要点与一个值得留意的边角
    
  
    
    
    操作只被借用，不被取消
    select! 里写的是 &mut operation，输掉一轮不会 drop future。stopping 时非 Resize 的 Busy 原样放回；teardown 的 future 同样会一直 poll 到结束。
    main_loop.rs:1-3, 74-77, 509-520
    
    
    失败不回到出发状态
    Transition::finish 失败时返回 Live<F>，FailedMachine 只有 teardown()。Controller 里没有能容纳 F 的变体，"失败后继续服务"在类型上不可表示。
    controller.rs:115-122, 391-406
    
    
    事件先于完成和请求
    biased select 保证同时就绪时先处理事件；第 ⑤ 步再补收 operation 最后一次 poll 时入队的事件。teardown 期间事件也继续被合并。
    main_loop.rs:318-363, 104-125, 504-524
    
    
    回复总有着落
    Busy 状态持有触发它的 reply，在 finish 时回答；shutdown_resize 清理失败时回答 ResizeUnavailable。被丢弃的只有准入关闭时尚未出队的请求，客户端得到 NoReply。
    controller.rs:352-406 · main_loop.rs:449-457
    
    
    内存服务按 owner 检查，不看任务名
    设备退出事件只警告（局部故障就地隔离）。是否失去 RAM 依赖由 failed_memory_service() 查询实际持有的服务句柄，在第 ① 和第 ④ 步各查一次。
    controller.rs:541-547 · main_loop.rs:54-63, 84-103
    
    
    同步构建是唯一的阻塞例外
    start() 在 vmm-main 上读取 kernel / initrd 并构建 parked 机器，此时还没有 guest 代码运行。build 部分失败后的 pending.wait(4s) 放进 Starting 的 operation，而不是同步外壳。
    main_loop.rs:253-306
    
  
    
  
    
    
    值得留意：先到的 Shutdown 会"吸收" reset，使结果依赖到达顺序
    
    
    GuestReset 有两个来源：i8042 设备（vCPU 继续存活），以及 KVM 的 shutdown / system-reset 退出（vcpu.rs:925-928）——后者会让该 vCPU 线程以 Ending::Reset 结束，之后发给它的命令得到 VcpuError::Exited。TransitionExited 的设计意图是"由事件进一步解释"：若同时有 reset，就保留 reset，结果为 Ok。
    
    
    但当 stopping 已经是 Shutdown 时：
    
    
      
      
    1. reset 事件到达：prefer_exit(Some(Shutdown), GuestReset) 命中 (Some(prior), _)，保留 Shutdown，reset 这一事实被丢掉；
      2. 
      
    2. 随后 Pausing / Resuming（或 Starting 的首次 resume）因该 CPU 已退出而失败：prefer_exit(Some(Shutdown), TransitionExited) 命中 (_, fallback @ TransitionExited)；
      3. 
      
    3. 最终 VmmExitStatus::Error(…)。若 reset 事件晚于完成才被观察到，则会走 (Some(TransitionExited), GuestReset)，结果是 Ok。
      4. 
    
    
    
    这是按代码推导的结论，没有在 KVM 上复现；现有测试 cpu_failure_precedence_distinguishes_exited_from_fatal_errors 只覆盖了"Shutdown + 失败、无 reset"。一种可能的修正是让 GuestReset 在与 Shutdown / Detached 合并时胜出——三者都映射为 Ok，其他结果不受影响。
