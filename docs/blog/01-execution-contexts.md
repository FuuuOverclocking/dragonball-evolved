# 一：一个 VMM 进程需要几种执行上下文

`KVM_RUN` 是阻塞 ioctl：把 vCPU 交给内核以后，这个调用不返回，直到客户机因为 MMIO、PIO、HLT 或者信号退出。
块设备读写、网络收发、vhost-user 握手正好相反，它们是发起之后等待完成，用异步写最自然。

两类代码放进同一个进程，首先要定的是线程划分。

## vCPU 能不能交给异步运行时

Tokio 提供 `spawn_blocking`，把 `KVM_RUN` 当作阻塞操作提交给阻塞线程池，看上去可行。问题出在停止路径上。

停止一个 vCPU 的做法是 `immediate_exit` 加定向信号加 join：先设置共享标志，再向运行该 vCPU 的那条线程发送 `SIGRTMIN`，使它从 `KVM_RUN` 返回，然后 join 它。
这要求线程身份稳定、能定位到具体线程、生命周期由 VMM 决定。阻塞线程池三条都不满足：池内线程可复用，何时回收由运行时决定。

所以 vCPU 使用独立的 OS 线程，一个 vCPU 一条，不进入运行时。它的职责范围也随之固定：执行 `KVM_RUN`、同步处理 MMIO/PIO 退出、把终止原因通过 typed channel 发回 vmm-main，不做异步设备 I/O。

## 设备运行时选多线程还是单线程

多线程运行时要求 task 满足 `Send`，于是设备的仿真状态必须能跨线程移动：队列状态、请求上下文、后端连接要么 `Send + Sync`，要么放进 `Arc<Mutex<...>>`。

放进锁以后，设备的热路径（取描述符、读写数据、写 used ring）每次都要加锁，而这条路径上没有并发：一个队列在同一时刻只有一个后端在处理。锁保护的是不存在的竞争。

改用单线程 LocalRuntime（`#[tokio::main(flavor = "local")]`）之后，设备 task 可以持有 `!Send` 状态，所有权唯一，热路径不加锁。
真正需要跨线程共享的部分数量有限，而且可以逐项列出：配置空间、队列配置、中断线。它们由 vCPU 线程同步访问，各自放在自己的 `Arc<Mutex<...>>` 后面，而不是把整个设备锁起来。

## main 线程做什么

第三个上下文是 CLI、API、TUI 和信号处理。它们不应访问 VM 内部状态，VM 也不应因为前端阻塞而停止工作。
所以 main 线程只持有 `VmmClient`，通过 channel 与 vmm-main 通信，`vmm::start()` 返回的就是这个句柄。

这条边界还让 VMM 可以作为库使用：嵌入者可以在一个进程里启动多个互不相干的 VMM。
集成测试 `several_vmms_run_side_by_side_in_one_process` 检查的正是这一点，只要有 `static` 或 `OnceLock` 形式的进程级状态混入，它就会失败。

## 四种上下文的职责

| 执行位置        | 主要职责                                        | 不应承担                |
| --------------- | ----------------------------------------------- | ----------------------- |
| main            | CLI、API、TUI、信号处理                         | VM 内部状态和设备数据面 |
| vmm-main        | 生命周期、请求分发、异步设备、vhost-user 控制面 | 阻塞 `KVM_RUN`          |
| vcpu-N          | `KVM_RUN`、同步 MMIO/PIO 退出                   | 异步设备 I/O            |
| vhost-user 进程 | 外部 virtqueue 数据面                           | VM 全局生命周期         |

## 单线程带来的两条约束

后面几篇会多次用到这两条：

- 请求处理函数不能长时间占用 vmm-main。耗时的操作应把 `Reply` 移入一个 task，由它稍后回答。
- 大块 RAM 拷贝、迁移流读写这类以百毫秒计的 I/O，要交给专门的 writer 或 worker，不能留在 vmm-main 上。

代价换来的是：设备热路径不加锁，vCPU 的停止过程可控，前端与 VM 解耦。
