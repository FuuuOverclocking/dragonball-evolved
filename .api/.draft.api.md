- 通过 API 的编译时反射, 最终产生下列内容, 并且相互一致
    - 本体: `enum VmmRequest { Req1(Req1, Reply<Resp1>), .. }`
        - API crate 的基本单元是 Vmm 请求列表
        - Reply 通常是一个 `oneshot::Sender<T>`, 用于一对一地发回返回值
        - metadata 自描述请求, 提供各个命令及其字段内容的描述
    - 配置文件
        - serde 反序列化: 先变为 serde_json::Value, 接着前缀匹配, 最后得到 `Vec<VmmRequest>`
        - JSON Schema: 利用前缀和 rustdoc 注释生成
        - 配置模板: 预置, 实际不包含在生成过程中, 但内容要一致 (人工检查)
        - 特例: 存在哪些? 如何允许扩展?
        - 要求:
            - Req 和 Resp 均实现 Ser/De
            - 标注 `config: ".aa.bb.cc[]"` 作为前缀
    - RESTful API
        - Router: 通过匹配 HTTP 方法和路径, 转成特化的请求
        - OpenAPI YAML: 基于 HTTP 方法和路径, rustdoc 生成
        - 特例: 存在哪些? 如何允许扩展?
        - 要求:
            - Req 实现 Ser/De, Resp 实现 IntoResponse (status code, body)
            - 标注 `route: GET /api/v1/xx` 提供 HTTP 方法和路径
    - 配置文件和 RESTful API 均不允许 key 键 (例如 `/drives/{id}`, `.drives.{id}`), 或者其他扩展 path 的需求
    - CLI/REPL
        - 这里存在较多问题, CLI 经常经过自定义, 以满足简短的需求, 或者改变结构, 从嵌套改为平整
        - 提供默认实现如下
            ```sh
            dbcli insert-block-device <<EOF     # Req 改为小写和 "-" 分隔, 作为命令; stdin 为 toml 格式, 作为命令内容
            drive_id = "blk1"
            path_on_host = "/tmp/blk1.ext4"
            EOF
            ```
        - 自行扩展: 标注 `cli: path::to::mod`
            - `mod::cmd` 需要返回 `clap_builder::builder::command::Command` 作为子命令
                - 子命令会被填入主命令的 `.subcommands([ ])`
            - `mod::parse` 需要接受 `&ArgMatches`, 返回 `Result<VmmRequest>`
                - 来自 `cli.get_matches().subcommand_matches(cmd_name)`, 已经匹配到了当前这一级

### 第一阶段：可编译的单一声明 API 骨架

目标：用真实 VMM 请求验证类型关联和装箱边界，而不是先写完整生成器。

1. 在 api 内建立一份操作声明，以轻量 macro_rules 生成请求类型、无通道命令类型和操作级 metadata；不增加 api 对工作区宏 crate 的依赖。
2. 优先以 GAT 编码 Reply 类型族：命令模式使用 ()，执行模式使用 Reply<T>；参数是普通 Ser/De 数据。编译与调用测试检验是否足够，不为模拟高阶类型先搭建 OUT_DIR 构建系统。
3. 保留同步/异步 typed reply 路径；非默认 wire feature 提供从无通道命令创建执行请求和异构回复等待器的适配。只在异构回复边界装箱，输出 JSON Value 不代表已经确定 HTTP 响应协议。
4. 实现 Shutdown、Status、GetInstanceInfo 三项真实请求。InstanceInfo 的对外数据类型由 api 定义，vmm 使用它；不实现假的 UpdateLogger、设备或恢复处理器。
5. 接入现有 VMM 和调用点，确保回复类型静态关联、跨线程发送、客户端放弃等待和关闭完成语义正确。
6. 将 src/config/parse.rs 的数组继承改为整体替换，并补齐嵌套、空数组、多级继承测试。
7. 使用测试专用操作覆盖带参数请求、Result 响应、异构回复和失败传播，避免三个无参生产请求掩盖泛型设计缺陷。

验收：

- 同一操作列表驱动命令、执行请求、名称/文档 metadata 和 wire 适配；没有手工维护第二份请求/响应列表。
- api 无工作区依赖；默认 feature 不启用 wire、CLI 或文档导出依赖；wire 关闭与开启均可编译测试。
- 构造纯命令不创建 channel；准备执行才创建 channel；不同请求不能误配回复类型。
- 保留直接调用者的具体返回类型，不引入大一统 VmmResponse，也不把 JSON 带进 VMM 业务分发。
- 对 Shutdown、Status、GetInstanceInfo 运行真实 VMM 集成测试；对异构等待器验证成功、业务 Result、断开和放弃等待。
